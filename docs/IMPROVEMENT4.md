# IMPROVEMENT4.md — multi-sport support (Badminton + Tennis)

Status: concept, confirmed with the user via a one-question-at-a-time
interview on 2026-08-10 (see conversation history for the full Q&A — this
document is the resulting spec, not a proposal). Read this after
`IMPROVEMENT.md`/`IMPROVEMENT2.md`/`IMPROVEMENT3.md`/`SPEC.md`/`PLAN.md`.
This patch adds a second sport (Tennis) alongside the existing Badminton
support, reusing every existing feature and screen — matchmaking, scoring
engine, tournament lifecycle, both scoreboards — unchanged, gated behind a
new sport-selection step and a per-sport split of player skill level.

**This is the largest schema/architecture change since Phase 13.** Unlike
`IMPROVEMENT2.md`/`IMPROVEMENT3.md` (behavioral corrections on an existing
data model), this patch changes what a "match count" or "skill level" _is
scoped to_ — every player now has two independent skill/stat identities
(one per sport) instead of one. Read §3 (schema) and §4 (`player_stats`
rewrite) carefully before touching code; nearly every feature module reads
from `player_stats` or `tournaments.type` in some way and needs a `sport`
value threaded through.

Do not write implementation code yet. Enter Plan Mode first, propose the
concrete step sequence (this document gives the shape of the change, not
an ordered implementation plan), and wait for approval before touching
`src/`, `src/lib/database.types.ts`, or the Supabase schema.

## 0. Decisions confirmed during the interview (do not re-litigate)

1. **Skill level split covers both fields**, not just the self-selected
   one: `self_selected_level` AND the win-rate-derived `effective_level`
   are both independently tracked per sport. A player's Tennis stats never
   affect their Badminton level or vice versa.
2. **Every tab (Create/Active/Scoreboard/History/Member) filters to the
   currently selected sport.** There is no "show both sports at once" view
   anywhere. The selected sport is effectively a workspace.
3. **A new Home screen** (icon picker, reusing the existing `IconChoice`
   component) gates entry: first-ever visit shows Home with no bottom nav;
   after a sport is chosen it's remembered (`localStorage`) and later app
   opens skip straight past Home into that sport's tab flow. A **persistent
   switcher control** in the nav/header (not just a one-time choice) lets
   the organizer return to Home and pick the other sport at any time.
4. **Tennis reuses the badminton scoring engine exactly as-is** —
   games-per-match / points-per-game / win-by / BWF-ratio deuce cap. This
   is **not** real tennis scoring (no sets, no 40-40/advantage, no
   tie-break). No scoring-engine code changes at all; only a `sport` tag
   on the tournament.
5. **Matchmaking algorithm is unchanged and shared** — equal match count →
   (doubles: gender balance hard filter) → skill balance → gender balance
   (singles) / avoid repeat → avoid repeat. No sport-specific branches in
   `src/features/matchmaking/`. A tournament's `sport` only ever affects
   _which_ `player_stats` row (self-selected/effective level, match count)
   feeds the algorithm — never the algorithm's logic.
6. **Self-selected level at entry time is scoped to the active workspace
   only.** Creating a member (or editing their level) while in the Tennis
   workspace sets/edits `tennis_self_selected_level` only; the other
   sport's level is untouched.
7. **All existing data migrates to Badminton.** Every existing tournament/
   match is tagged `sport = 'badminton'`. Every existing member's current
   `self_selected_level` becomes their `badminton_self_selected_level`;
   `tennis_self_selected_level` starts `NULL` for everyone, with no
   exceptions.
8. **Home-screen icons: user-supplied image files**, not generated by
   Claude. Implementation should leave a clearly-named placeholder path
   (e.g. `src/assets/icons/sport_badminton.png` / `sport_tennis.png`) and
   flag it as a blocking dependency until the user supplies the files —
   same pattern as the app's other `src/assets/icons/*.png` assets.
9. **A member missing the active sport's level cannot be selected as a
   tournament participant.** The Create-tournament participant checklist
   (and any future add-participant picker) must exclude or disable members
   whose `{sport}_self_selected_level` is `NULL` for the active workspace.
   They become selectable only after visiting Member and setting that
   level via a new inline "set level" affordance (§6).

## 1. New concept: "sport workspace"

Introduce a single source of truth for "which sport is currently active,"
read by nearly every page and query:

- `src/features/sport/sportTypes.ts` — `export const SPORTS = ['badminton',
'tennis'] as const; export type Sport = (typeof SPORTS)[number]`.
- `src/features/sport/SportContext.tsx` — React context + provider holding
  `{ sport: Sport | null, setSport: (s: Sport) => void }`. `null` means "no
  sport chosen yet" (first-ever launch). On mount, initializes from
  `localStorage` (`racket-score:selectedSport`, mirroring how
  `passphraseStore.ts` already persists session state — check that file's
  storage-key convention before naming this one). `setSport` writes through
  to `localStorage` immediately (this choice persists across browser
  restarts, unlike the passphrase).
- `src/features/sport/useSport.ts` — thin hook wrapping the context,
  throwing if used outside the provider (matches this codebase's existing
  context-hook style — check `usePassphraseGate.ts` for the pattern to
  mirror).

`main.tsx`/`App.tsx` wraps the router in `<SportProvider>`, alongside the
existing `PassphraseGateProvider`/`QueryClientProvider`.

## 2. Routing & navigation changes

- `src/pages/HomePage.tsx` (new) — full-screen sport picker using
  `IconChoice<Sport>`, two options (badminton/tennis) with the
  user-supplied icons (§0.8). Selecting a sport calls `setSport` then
  navigates to `/create`. No bottom nav rendered on this route (it should
  **not** be inside `<AppLayout>`'s `<Outlet>` — give it its own top-level
  `<Route>` outside the `AppLayout` element, or a layout flag that hides
  `.tab-bar`).
- `App.tsx`: add `<Route path="/home" element={<HomePage />} />` **outside**
  the `<AppLayout>`-wrapped route group. Add a guard on the index route: if
  `sport === null`, `<Navigate to="/home" replace />`; else `<Navigate
to="/create" replace />` (unchanged from today once a sport exists).
  Every other route (`/create`, `/active`, `/tournaments/:id`, `/scoreboard`,
  `/history`, `/member`) needs the same "no sport selected → redirect to
  /home" guard, since a user could deep-link or reload on one of them
  before ever picking a sport — simplest is a small wrapper route element
  checked once in `AppLayout` itself (redirect from there if `sport ===
null`, before rendering `<Outlet>`).
- `AppLayout.tsx` (~line 18-41): add a sport-switcher button in
  `.app-header` next to `LanguageToggle`, showing the current sport's icon/
  label, linking to `/home`. `/home` stays reachable at any time this way,
  distinct from the first-launch redirect.

## 3. Schema changes

Two migrations (via `apply_migration`, then `generate_typescript_types` to
refresh `src/lib/database.types.ts` — do not hand-edit that file).

**Migration A — split player skill level by sport:**

```sql
alter table public.players
  add column badminton_self_selected_level text,
  add column tennis_self_selected_level text,
  add constraint players_badminton_level_check
    check (badminton_self_selected_level is null or
           badminton_self_selected_level = any (array['beginner','intermediate','advanced','pro'])),
  add constraint players_tennis_level_check
    check (tennis_self_selected_level is null or
           tennis_self_selected_level = any (array['beginner','intermediate','advanced','pro']));

update public.players
  set badminton_self_selected_level = self_selected_level;

alter table public.players
  drop column self_selected_level;
```

Both new columns are **nullable** (unlike the old single column, which was
`NOT NULL`) — a player can legitimately have no level yet for a sport
they've never been entered into.

**Migration B — tag tournaments with a sport:**

```sql
alter table public.tournaments
  add column sport text not null default 'badminton',
  add constraint tournaments_sport_check
    check (sport = any (array['badminton','tennis']));
```

The `default 'badminton'` both backfills every existing row correctly
(§0.7) and is harmless to leave in place afterward — `create_tournament`
will always pass an explicit `p_sport` going forward, so the default only
matters for this one-time backfill semantics, not as an ongoing behavior.

**RPC changes** (re-`CREATE OR REPLACE FUNCTION`, same
passphrase-gated pattern as every existing write path — see
`check_write_passphrase` calls in the current definitions):

- `create_player(p_name, p_gender, p_sport, p_self_selected_level,
p_passphrase)` — inserts with only the `{p_sport}_self_selected_level`
  column set (dynamic column name needs `format('%I',
p_sport||'_self_selected_level')` + `execute`, or simpler: an `if
p_sport = 'badminton' then ... else ... end if` branch — plain
  conditional SQL is clearer than dynamic SQL here and matches this
  codebase's preference for explicit code over cleverness).
- `update_player(p_id, p_passphrase, p_name, p_gender, p_sport,
p_self_selected_level)` — same per-sport branch, `coalesce`-updates only
  the column matching `p_sport`; `p_sport`/`p_self_selected_level` must
  both be provided together or both omitted (mirrors existing
  `coalesce(p_x, x)` pattern for optional updates — passing `p_sport` but
  not `p_self_selected_level`, or vice versa, should probably raise rather
  than silently no-op; confirm this edge case doesn't matter in practice
  before over-engineering it).
- `create_tournament(..., p_sport, p_passphrase, p_win_by default 2)` —
  adds `p_sport` to the insert.

## 4. View changes — `player_stats` becomes sport-scoped (2 rows/player)

This is the load-bearing change. Today `player_stats` has **one row per
player**, aggregating match history across all tournaments regardless of
type. It must become **one row per (player, sport)** — two rows per
player, always present even with zero matches in a sport, so every call
site can `.eq('sport', activeSport)` and get exactly one row per player
back, same shape as today.

Rewrite (`create or replace view public.player_stats as ...`), keeping the
existing CTE structure but scoping `player_match_results`/`player_agg` by
the tournament's `sport`, and cross-joining players against both sports so
never-played-that-sport players still get a row:

```sql
create or replace view public.player_stats as
with team_games_won as (
  select match_games.match_id,
    sum(case when team1_score > team2_score then 1 else 0 end) as team1_games,
    sum(case when team2_score > team1_score then 1 else 0 end) as team2_games
  from public.match_games
  group by match_games.match_id
),
match_winners as (
  select m.id as match_id, m.tournament_id,
    case when tgw.team1_games > tgw.team2_games then 1
         when tgw.team2_games > tgw.team1_games then 2
         else null end as winning_team
  from public.matches m
  join team_games_won tgw on tgw.match_id = m.id
  where m.status = 'completed'
),
player_match_results as (
  select mp.player_id, t.sport, (mp.team = mw.winning_team) as won
  from public.match_participants mp
  join match_winners mw on mw.match_id = mp.match_id
  join public.tournaments t on t.id = mw.tournament_id
),
player_agg as (
  select player_id, sport,
    count(*) as total_matches,
    count(*) filter (where won) as total_wins
  from player_match_results
  group by player_id, sport
),
sports as (select unnest(array['badminton','tennis']) as sport)
select
  p.id as player_id,
  p.name,
  p.gender,
  s.sport,
  case when s.sport = 'badminton' then p.badminton_self_selected_level
       else p.tennis_self_selected_level end as self_selected_level,
  coalesce(pa.total_matches, 0) as total_matches,
  coalesce(pa.total_wins, 0) as total_wins,
  case when coalesce(pa.total_matches, 0) = 0 then null
       else round(pa.total_wins::numeric / pa.total_matches::numeric * 100, 2)
       end as win_rate,
  case when coalesce(pa.total_matches, 0) < 3 then
         case when s.sport = 'badminton' then p.badminton_self_selected_level
              else p.tennis_self_selected_level end
       when (pa.total_wins::numeric / pa.total_matches::numeric * 100) >= 75 then 'pro'
       when (pa.total_wins::numeric / pa.total_matches::numeric * 100) >= 50 then 'advanced'
       when (pa.total_wins::numeric / pa.total_matches::numeric * 100) >= 25 then 'intermediate'
       else 'beginner' end as effective_level
from public.players p
cross join sports s
left join player_agg pa on pa.player_id = p.id and pa.sport = s.sport;
```

(Above is a starting draft, not final SQL — re-verify column names/types
against the live view definition fetched via `execute_sql` at
implementation time, and confirm the `< 3 matches → self-selected, else
win-rate band` threshold logic is copied exactly, since it's
security/correctness-sensitive matchmaking input, not cosmetic.)

`player_match_history` (used by `listPlayerMatchHistory` /
`useOverallScoreboard.ts` / `HistoryPage.tsx`) needs one added column:
`t.sport as sport` alongside its existing `tournament_type` column (same
join it already has to `tournaments`). `tournament_standings` needs **no
change** — it's already scoped to a single `tournament_id`, and a
tournament now has exactly one fixed `sport`, so nothing there depends on
cross-sport aggregation.

## 5. Application-layer call sites that need a `sport` parameter threaded through

Every one of these currently has no sport awareness and will silently mix
both sports' data (or break outright once `player_stats` doubles its row
count) if left unchanged:

- **`src/features/players/playersApi.ts`**: `getPlayerStats(playerId,
sport)` / `listPlayerStats(sport)` — both need a required `sport` arg,
  `.eq('sport', sport)` added to the query. `createPlayer`/`updatePlayer`
  need `sport` threaded into their RPC calls (§3).
- **`src/features/players/usePlayerStatsList.ts`** /
  **`usePlayers.ts`**: the stats hook needs to read `sport` from
  `useSport()` and include it in the query key (`['playerStats', sport]`)
  so switching workspaces invalidates/refetches correctly; `usePlayers`
  itself is unchanged (the member list — as opposed to stats — is not
  sport-scoped, per §0.2/§6 below).
- **`src/features/tournaments/tournamentsApi.ts`**: `createTournament`
  needs `sport` in `CreateTournamentInput`; `listTournaments()` needs a
  `sport` param + `.eq('sport', sport)` (used by `useTournaments.ts`,
  consumed by `ActivePage.tsx` and `HistoryPage.tsx`'s tournament list).
- **`src/features/matches/useDrawInputs.ts`** (`assembleDrawInputs`,
  ~line 24-71): `listPlayerStats()` call needs the tournament's own
  `sport` (fetch the tournament row, or accept it as a param from the
  caller who already has it) — a tournament's matchmaking must only ever
  read that one sport's `player_stats` rows, never mix in the other's.
- **`src/features/scoreboard/scoreboardApi.ts`**
  (`listPlayerMatchHistory`) / **`useOverallScoreboard.ts`**
  (`fetchOverallScoreboard`): add a `sport` filter (from `useSport()`)
  alongside the existing `since`/`tournamentType` filters — Overall
  Scoreboard is workspace-scoped per §0.2, with no user-facing sport
  toggle (the existing period/match-type filters are unaffected and stay
  as they are).
- **`src/pages/HistoryPage.tsx`**: both the "by match" and "by tournament"
  sections need the same `sport` filter as Active/Scoreboard.
- **`src/pages/CreateTournamentPage.tsx`** (~line 43-95, 171-196): pass
  `sport` from `useSport()` into the `createTournament` mutation; the
  participant checklist (~line 171-196) must read the sport-scoped
  `self_selected_level`/`effective_level` from `player_stats` (already
  sport-filtered per the hook change above) and, per §0.9, disable/exclude
  any player whose level for the active sport is `null` (with a `title`/
  tooltip explaining why, following the existing disabled-Remove-button
  convention in `PlayerList.tsx`).

## 6. Member page changes

- **`src/features/players/CreatePlayerForm.tsx`**: the level `<select>`
  sets only the active workspace's level (§0.6) — pass `sport` from
  `useSport()` into `useCreatePlayer`'s mutation.
- **`src/features/players/EditablePlayerLevel.tsx`** (currently reads/
  writes `player.self_selected_level` directly, ~line 19-54): rework to
  take the sport-scoped `PlayerStats` row (already sport-filtered) and a
  `sport` prop; `mutate({ id, updates: { sport, self_selected_level:
level } })`. **New case to handle**: when the active sport's
  `self_selected_level` is `null` (member exists but never set a level for
  this sport, §0.9) — render a distinct "not set — choose a level" prompt
  state (not just treat it as an editable existing value) that's really
  the same edit UI, just with no current value and probably a copy
  difference (e.g. `member.levelNotSet` i18n key) so it doesn't look like
  a bug. This is the same component/flow as the existing <3-matches
  editable state, just with an empty starting value instead of a
  pre-filled one.
- **`src/features/players/PlayerList.tsx`**: passes the sport-scoped stats
  down; no structural change otherwise (still lists every member
  regardless of whether they have a level in the active sport, per §0.2's
  member-pool-stays-shared assumption — confirm this reading is still
  correct at implementation time, since it wasn't asked as an explicit
  question).

## 7. i18n

New keys needed in both `src/i18n/en.json` and `th.json` (existing
top-level namespaces: `nav`, `member`, `players`, `tournaments`, `app`,
etc. — follow that structure):

- `home.*` — heading/instruction copy for the Home screen.
- `sport.badminton` / `sport.tennis` — display labels (used on Home, the
  nav switcher, and anywhere a sport name is shown).
- `nav.switchSport` (or similar) — the switcher button's label/aria-label.
- `member.levelNotSet` — the "no level yet for this sport" state (§6).
- `tournaments.form.participantMissingLevel` (or similar) — disabled-
  checklist-row tooltip explaining why a member can't be selected (§0.9).

## 8. Testing implications (flag, not exhaustive)

The existing suite has real coupling to the current single-level,
single-sport shape that will break on this change, not just need new
cases added:

- Any fixture/mock constructing a `players` row or `PlayerStats` with
  `self_selected_level` needs updating to the two-column split.
- `player_stats`-shaped test doubles need a `sport` field and (if a test
  asserts exact row counts from `listPlayerStats()`) awareness that the
  view now returns 2 rows per player, not 1.
- `useDrawInputs`/matchmaking integration tests that create real fixture
  tournaments need an explicit `sport` (defaulting to `'badminton'` keeps
  them passing unchanged, per §0.7's migration default).
- `fairnessInvariant.test.ts` and other pure-`matchmaking/` unit tests are
  **not** expected to need changes (§0.5 — no sport-specific branching in
  that module).
